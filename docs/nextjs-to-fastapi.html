Cadence · migration reference

Next.js API routes → FastAPI, for someone who already knows Next.js

Every comparison below is real code from this migration: the TypeScript is from 82d8b2a^ in cadence-frontend, the commit that deleted the backend; the Python is the file that replaced it. Nothing is invented for illustration.

The migration removed 4,104 lines of TypeScript across 15 server files. Almost every one has a direct Python counterpart, so the fastest way to learn the Python is to read it next to the TypeScript you already understand.

01Shape of the thing

Before: one process. After: two.

In Next.js the API route ran inside the same app that served the UI. Server code and client code shared a repo, a build, a deployment and a language. That is genuinely convenient, and losing it is the real cost of this migration — not anything about Python.

Now the frontend is a browser app that talks HTTP to a separate service. The boundary is the API and its schemas; the frontend has no access to the database, the model provider, or anything behind them.

Two things simply disappear

// more across many queries.

Why this matters for learning

A lot of Next.js server code is defensive against the framework — marking routes dynamic, fencing server-only modules, working around the bundler. When you read the Python and it looks sparse, that is usually because those concerns were framework-shaped and did not survive the move, not because something was dropped.

The one habit to build

Prefix commands with uv run. It resolves the venv for you, so uv run pytest works from anywhere in the repo without activating anything. Forgetting it is the most common way to run the wrong Python and get a confusing ModuleNotFoundError.

03Modules and imports

No @/ alias, no relative-path spaghetti — absolute package paths.

tsapp/api/chat/route.ts
import { runAnalyst, titleFor }
  from "@/lib/server/analyst";
import type { AnswerBlock, TraceStep }
  from "@/lib/types";
pyapi/chat.py
from cadence_backend import analyst

    append_message, create_conversation,
)

    CalloutBlock,
)
  • src/cadence_backend/ is the package. Every import starts from its name — there is no alias to configure because the package is the root.
  • __init__.py makes a directory a package, and doubles as the re-export surface — the closest thing to index.ts. That is why from cadence_backend.conversations import append_message works without naming store.py.
  • There is no import type. Python imports are always real, and types are ordinary objects at runtime — which is the whole basis of §9.

04Routing

File-path routing gives way to an explicit router object.

tsapp/api/chat/route.ts
// The path IS the file location.
// POST /api/chat

export async function POST(
  request: Request
) {
  // ...
}
pyapi/chat.py
router = APIRouter(prefix="/api",
                   tags=["chat"])

@router.post("/chat")
async def chat(request: wire.ChatRequest):
    ...

Routers are then mounted explicitly:

# src/cadence_backend/main.py
app.include_router(chat.router)
app.include_router(conversations.router)
What you gain and lose

You lose "the URL is the folder", which is genuinely nice for finding things. You gain routes that can be grouped, prefixed and mounted independently, and tags that organise the generated API docs.

That last point is not cosmetic: FastAPI serves an OpenAPI schema at /openapi.json and browsable docs at /docs, both derived from these decorators and the types below. Next.js had no equivalent — the contract lived in whatever the two sides agreed on.

05Request validation

The single biggest change in how the code reads.

tsapp/api/chat/route.ts
interface ChatRequest {
  question?: string;
  conversationId?: string | null;
  model?: string;
}

let body: ChatRequest;
try {
  body = await request.json();
} catch {
  return Response.json(
    { error: "Invalid JSON body." },
    { status: 400 });
}

const question = body.question?.trim();
if (!question) {
  return Response.json(
    { error: "A question is required." },
    { status: 400 });
}
pyschemas/chat.py
class ChatRequest(CamelModel):
    question: str
    conversation_id: str | None = None
    model: str | None = None

    @field_validator("question")
    @classmethod
    def _require_question(cls, value: str):
        question = value.strip()
        if not question:
            raise ValueError(
                "A question is required.")
        return question

The route body then contains none of that. Declaring the parameter as request: wire.ChatRequest is what makes it happen.

The mental shift

In TypeScript, interface ChatRequest is a compile-time claim that is erased before the code runs — await request.json() returns whatever arrived, and the interface is a promise you check by hand.

A Pydantic model is a runtime object. The same declaration parses the body, coerces types, applies validators, returns a 422 naming the bad field, and generates the OpenAPI schema. The type is not a claim about the data — it is the code that enforces it.

Watch for — camelCase on the wire

Python names are snake_case; the browser sends camelCase. CamelModel (our base, in schemas/base.py) sets an alias generator so conversation_id accepts and emits conversationId. Field names in Python, alias names on the wire — never rename a field to make JSON line up.

06Responses and errors

tsapp/api/conversations/route.ts
const conversation =
  await loadConversation(id);
if (!conversation) {
  return NextResponse.json(
    { error: "Not found" },
    { status: 404 });
}
return NextResponse.json(conversation);
pyapi/conversations.py
conversation = await load_conversation(
    conversation_id)
if conversation is None:
    raise HTTPException(
        status_code=404,
        detail="Not found")
return conversation
  • Return the object, not a response. FastAPI serialises the returned model using response_model, so the happy path has no wrapper call at all.
  • Errors are raised, not returned. raise HTTPException(...) unwinds to a handler. Coming from TypeScript the instinct is to return an error shape; here that would be serialised as a successful body.
  • Validation errors are automatic. Nothing in the route produces the 422 — it comes from the type annotation.
One thing we had to override

FastAPI's default validation response echoes the offending input back to the caller. main.py replaces it with one that names the failing fields and nothing else — echoing input back is a small information leak, and worth knowing the default does it.

07Streaming

Where the Python is dramatically shorter, and the reason is a language feature.

tsapp/api/chat/route.ts
const encoder = new TextEncoder();
const stream = new ReadableStream({
  async start(controller) {
    const send = (event) =>
      controller.enqueue(encoder.encode(
        `${JSON.stringify(event)}\n`));

    try {
      send({ type: "conversation", ... });
      // ...
    } finally {
      controller.close();
    }
  },
});

return new Response(stream, {
  headers: {
    "Content-Type":
      "application/x-ndjson; charset=utf-8",
    "Cache-Control": "no-cache, no-transform",
    "X-Accel-Buffering": "no",
  },
});
pyapi/chat.py
async def analyst_stream(
    request: wire.ChatRequest
) -> AsyncIterator[str]:
    yield format_sse("conversation", ...)
    # ...


return StreamingResponse(
    analyst_stream(request),
    media_type="text/event-stream",
    headers=STREAM_HEADERS,
)
Why it collapses

An async def containing yield is an async generator, and a generator is a stream. There is no controller to enqueue into, no encoder, no close() — the function ending closes the stream, and a Python finally still runs.

This is the closest thing in the migration to a language advantage rather than a framework one. ReadableStream is a general-purpose primitive you have to drive; an async generator is one the language drives for you.

One contract change, not a translation

Next.js sent NDJSON (application/x-ndjson, one JSON object per line). The Python sends SSE (text/event-stream, event: and data: lines). That was a deliberate change, not a port — SSE is a standard the browser understands natively. The frontend's readChatStream() sniffs the content type and handles both.

The two headers survived unchanged and are load-bearing in both: proxies buffer streaming responses by default, which defeats the point.

The one real trap

In Node, an un-awaited promise keeps running. In Python, a task with no reference can be garbage-collected mid-flight — the work silently stops. That is why api/chat.py holds them: 

_BACKGROUND_TASKS: set[asyncio.Task] = set()

def _detach(coro) -> None:
    task = asyncio.create_task(coro)
    _BACKGROUND_TASKS.add(task)
    task.add_done_callback(_BACKGROUND_TASKS.discard)

This exists for a real bug: when a client disconnects mid-answer, the engine turn still has to be persisted, and without holding the task that write sometimes vanished.

09Typing

Closer than you would expect. One line is character-for-character identical.

tslib/server/sources/types.ts
export interface SqlSource
    extends BaseSource {
  kind: "sql";
  schemaContext: string;
  traceLabel: string;
  query(sql: string): Promise<SqlOutcome>;
}

export type DataSource =
  SqlSource | DocumentSource;
pysources/types.py
@runtime_checkable
class SqlSource(Protocol):
    id: str
    kind: Literal["sql"]
    schema_context: str
    trace_label: str

    async def query(self, sql: str)
        -> SqlOutcome: ...


DataSource = SqlSource | DocumentSource
  • interface → Protocol. Both are structural: a class satisfies a Protocol by having the right members, with no implements and no inheritance. If you liked TypeScript interfaces, Protocols will feel like home.
  • Discriminated unions carry over. kind: "sql" becomes kind: Literal["sql"], and narrowing works the same way.
  • DataSource = SqlSource | DocumentSource is identical in both languages. Modern Python borrowed the | union syntax.
  • @runtime_checkable has no TS analogue — it lets isinstance(x, SqlSource) work at runtime, which a TypeScript interface can never do because it no longer exists by then.
The difference that matters

TypeScript types are erased at build time. Python annotations are objects that exist at runtime, which is how FastAPI reads a signature to build validation and docs, and how Pydantic enforces a schema. The same annotation does more work here — and unlike tsc, nothing checks it ahead of time unless you add a type checker.

10Database and shared state

The globalThis hot-reload hack has a much plainer replacement.

tslib/server/db.ts
declare global {
  var __cadenceAppPool: Pool | undefined;
}

export function appDb(): Pool {
  return (globalThis.__cadenceAppPool ??=
    new Pool({
      connectionString:
        process.env.DATABASE_URL,
      max: 5,
      idleTimeoutMillis: 30_000,
    }));
}
pydb/pool.py
_app_pool: asyncpg.Pool | None = None

async def app_pool() -> asyncpg.Pool:
    global _app_pool
    if _app_pool is None:
        _app_pool = await asyncpg.create_pool(
            get_settings()
                .require_database_url(),
            min_size=1, max_size=5,
            command_timeout=30,
        )
    return _app_pool

The llm.ts singleton used the same globalThis trick. Its Python counterpart uses a decorator instead: 

# src/cadence_backend/llm/client.py
@lru_cache
def llm() -> AsyncOpenAI:
    """The shared client. Raises only when actually used without a key."""
    ...
Why globalThis was needed and is not now

That hack exists because Next.js hot-reload re-evaluates modules, so a module-level new Pool() would leak a pool per reload until the database refused connections. Stashing it on globalThis survives re-evaluation.

Python's reloader restarts the process instead, so a module-level global is simply a singleton. @lru_cache on a zero-argument function is the idiomatic shorthand for the same thing.

What carried over unchanged

  • $1 placeholders — both pg and asyncpg use Postgres-native numbering, so queries moved across verbatim.
  • The pool size, the read-only analyst role, and the FORBIDDEN statement regex. The privilege boundary is in Postgres, not in either language.

11Config and secrets

tslib/server/llm.ts
if (!process.env.OPENROUTER_API_KEY) {
  throw new Error(
    "OPENROUTER_API_KEY is not set. " +
    "Copy .env.example to .env.");
}
export const MODEL =
  process.env.OPENROUTER_MODEL ||
  "anthropic/claude-opus-5";
pycore/config.py
class Settings(BaseSettings):
    app_name: str = "Cadence API"
    openrouter_api_key: SecretStr | None = None
    openrouter_model: str = (
        "anthropic/claude-opus-5")

    def require_openrouter_api_key(self) -> str:
        return _require(self.openrouter_api_key,
                        "OPENROUTER_API_KEY")
  • Typed and centralised. Every setting is declared once with a type and a default, rather than process.env.X reads scattered across files, each stringly-typed.
  • SecretStr has no Node equivalent. A plain str API key appears in repr(settings), and settings objects end up in log lines and tracebacks. SecretStr prints as **********.
  • Missing keys fail at point of use, not at import. The service still boots and answers /health without an API key — absent credentials mean the analyst cannot run, not that the service is unhealthy.

12Lifecycle and CORS

Two things with no Next.js counterpart, because one process needed neither.

# src/cadence_backend/main.py
@asynccontextmanager
async def lifespan(_: FastAPI):
    warmup = asyncio.create_task(_warm_corpus())   # before serving
    yield                                          # ← the app runs here
    warmup.cancel()                                # after the last request
    await close_pools()

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.frontend_origins,       # never "*"
    allow_credentials=False,
    allow_methods=["GET", "POST"],
    allow_headers=["Content-Type"],
)
  • Lifespan is startup/shutdown. Everything before yield runs once before the first request; everything after, once at shutdown. Serverless routes had nowhere to put this — there was no "before serving" to hook.
  • CORS is needed because the split happened. When the API lived inside the Next.js app it was same-origin, so the browser never asked. Now it is a different origin and the allowlist is the thing stopping any page from calling this API.
Also worth knowing: Depends

FastAPI has a dependency-injection system — Depends() — that most tutorials lead with, typically for database sessions and auth. This codebase uses it zero times: pools are module-level singletons and there is no auth. Worth recognising when you read FastAPI material elsewhere, but you will not find it here.

conftest.py — no direct analogue

Fixtures defined in conftest.py are available to every test in that directory without being imported. It also runs early, which this suite depends on: 

# tests/conftest.py — order is load-bearing
import os

os.environ["OPENROUTER_API_KEY"] = ""
os.environ["DATABASE_URL"] = ""

import httpx                              # noqa: E402
from cadence_backend.main import app      # noqa: E402  ← imported AFTER
Why the odd import order

Settings are read when the app module is imported. Import the app first and it captures a developer's real .env — the suite then called OpenRouter and Postgres for real, taking 71 seconds and costing money. Neutralising the environment first drops it to 0.04 seconds.

The noqa: E402 comments silence "imports must be at the top", because here they deliberately are not. Coming from vitest, where vi.mock is hoisted for you, this is the sharpest difference in the whole section: in Python, import order is program order.

14Gotchas that actually bit us

Every one of these is a real bug from this migration, with the symptom it produced.

1 · pydantic-settings JSON-decodes list fields before validators run

FRONTEND_ORIGINS=http://localhost:3000 crashed the service on boot. A field typed list[str] is JSON-parsed before any validator sees it, so a plain comma-separated string is invalid JSON and fails first. The fix: 

frontend_origins: Annotated[list[str], NoDecode] = Field(
    default_factory=lambda: ["http://localhost:3000"]
)

No Node equivalent — nothing parses process.env for you there.

2 · Mutable default arguments

The classic Python trap, with no TypeScript counterpart. A default like def f(items=[]) is created once and shared by every call, so appending to it leaks between calls. Use None and build inside, which is also why the settings field above uses default_factory rather than a literal list.

3 · asyncpg + a transaction-mode pooler

Supabase's pooler hands the same client different server connections between statements, so asyncpg's cached prepared statements are missing on the next one. It surfaces as a bewildering "prepared statement does not exist", usually on the very first request. Fixed with statement_cache_size=0 in db/pool.py.

4 · A placeholder that looks like IPv6

Leaving [YOUR-PASSWORD] in a connection string produced "does not appear to be an IPv4 or IPv6 address" — Python reads bracketed text in a URL as an IPv6 literal. The error names the wrong thing entirely.

5 · Secrets in a repr

A plain str API key on a settings object appears in full whenever that object is printed or lands in a traceback. SecretStr exists for this and costs one .get_secret_value() call at the point of use.
