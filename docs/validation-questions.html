Before you start

The backend log must say market_source=both, and you must wait for BM25 index: 119207 chunks … — about eighty seconds after boot. Ask before that and document search silently returns nothing, which looks like a missing feature rather than a warm-up.

How an answer is actually produced

Worth knowing before reading the results, because it is what makes them checkable: the analyst writes its own SQL and runs it. Nothing is templated, and every figure traces to a query you can expand in the app.

#StepWhat happens
1Prompt The model is given two tools — run_sql and search_documents — and the full schema of every registered source, including the documented traps and coverage gaps.
2It writes a query The SQL is the model’s own. It picks the source (market for Supabase, bellweather for Snowflake) and states a purpose, which becomes the label on the trace row.
3Guard The statement must begin SELECT or WITH, and a forbidden-keyword check blocks writes and USE ROLE. This is defence in depth — the real boundary is a database role granted SELECT and nothing else.
4Execute Supabase via asyncpg in an explicit read-only transaction; Snowflake via its connector on a worker thread, so one slow query cannot stall the stream. Up to 50 rows come back.
5Stream The SQL, its columns and its rows are pushed to the browser as a trace step immediately — before the answer exists.
6Loop Results re-enter the conversation and the model decides what to ask next, up to fourteen turns. This is why traces run three to fourteen steps: each query is chosen from the last one’s result.
7Compose A separate pass turns the accumulated evidence into answer blocks, so shaping the answer never competes with deciding what to query.
Why this is the anti-hallucination story

Numbers come from SQL that was executed, not from documents that were read. That is what lets the analyst contradict a document: asked about a licensing true-up the corpus asserts, it queried the ledger, found the account was a cost line with no spike, and rejected the claim. A retrieval-led design would have repeated it.

One thing that is a tendency, not a mechanism

The cross-checks in these answers — scaling the panel and comparing it to the census, or counting the helpdesk two ways — are the model choosing to corroborate, encouraged by the prompt. No code enforces them. It happened in every answer where it was relevant, but nothing guarantees it on the next question.

The most important answer in this set

The second question contains a false premise, planted by the corpus generator. The analyst did not repeat it. It checked content amortisation across all 30 months, found the period sits at the low end rather than showing a one-off charge, confirmed every subscriber measure moved favourably or flat, and then said:

“The ‘licensing true-up’ claim traces to a sentence repeated verbatim across six unrelated corpus documents with different quarters and services attached, which marks it as templated filler rather than a verified event.”

It detected a fabricated document by noticing the same sentence recurring with different entities attached — the same conclusion our own investigation reached, arrived at independently and inside a single answer.
