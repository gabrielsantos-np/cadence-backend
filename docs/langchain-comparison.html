Should the analyst loop be LangChain?

A comparison and a migration plan, written against the current LangChain API rather than a remembered one — which matters, because the six-line version usually quoted for this is now deprecated.

First, a correction to the obvious answer

The snippet everyone reaches for is create_sql_agent. LangChain’s own reference now says it returns a legacy AgentExecutor that is “not actively supported as the recommended foundation for new production applications”. The current path is create_agent with the SQL toolkit’s tools passed in.

What that costs the pitch

“Six lines replaces four hundred” was true of the deprecated API. On the supported one you write the model init, the toolkit, the system prompt, the agent, and then your own streaming and answer-composition layers — because those are not what the library provides. Still much less code than we have. Not six lines.

This is the whole decision, in one row of a table

Introspection gives column names, types and three sample rows. Ask an agent working from that for July 2025 churn and it will very reasonably divide by the closing base and answer 4.19% — plausible, confident, wrong. Ours answered 4.24% because the formula is written down.

custom_table_info is the escape hatch: a dict keyed by table name whose value replaces the generated description for that table. Our 117 lines of prose have somewhere to live. Verify this early — the whole migration rests on it, and the reference does not state whether it supplements or wholly replaces.

The risks worth pricing before starting

1 · Async — the one that could sink it

This stack is asyncpg end to end, inside an SSE generator. LangChain’s SQLDatabase is SQLAlchemy-based, so async means create_async_engine and a different driver path, and any synchronous call inside the request blocks the event loop for every other user. Unknown effort until spiked. Resolve this first; everything else is moot if it is bad.

2 · Snowflake

Adds snowflake-sqlalchemy on top of the connector we already use, and we already fight Snowflake’s SQL differences — no read-only transaction, no CHECK, no FILTER (WHERE …). A second abstraction over that dialect is a second place for those to bite.

3 · Dependency weight and churn

Eight direct dependencies today. This adds langchain, langchain-community, sqlalchemy and a Snowflake dialect. And the API moves: the canonical SQL-agent recipe was deprecated between versions, which is exactly the maintenance we would be buying to avoid.

4 · What does not change

Answer quality is set by the schema prose and the read-only role, and both survive the move untouched. So the honest expected outcome is the same answers, less of our code, more of theirs — not better answers.

The plan

Four phases, each with a gate. The first is a day and answers the only question that matters; stop there if it fails.

Phase 0 — spike, half a day to a day

  • One warehouse (Supabase MARKET), one question, behind a branch. No frontend work.
  • Prove custom_table_info carries the trap prose through to the model.
  • Prove an async SQLAlchemy engine works inside an async request without blocking.
  • Gate: ask the churn question. If it answers 4.19%, the prose is not reaching the model and the migration is off until it does.

Phase 1 — measure it, half a day and about $6

  • Point scripts/acceptance.py at the LangChain path with --cases data/market_truth_cases.json.
  • Gate: 18 of 18, matching what we score today. The harness, the ground truth and the cost accounting already exist — this is precisely what they were built for.

Phase 2 — the integration layers, two to three days

  • Map astream_events onto the SSE contract, keeping conversation / step / answer / error / done byte-identical — the contract tests and the frontend both depend on it.
  • Keep the composition pass exactly as it is.
  • Re-implement cost accounting as a callback handler.
  • Gate: the frontend renders traces with no change, and 104 tests pass.

Phase 3 — the second warehouse, one to two days

  • A second SQLDatabase for Snowflake; routing guidance moves into the system prompt as it is today.
  • Gate: 14 of 14 on the Snowflake set and 5 of 5 on the cross-source cases, which are the ones that prove both warehouses are genuinely in the path.
Why the gates are cheap

Every one is an existing command against existing ground truth. A rewrite of this kind normally has no way to tell whether it broke something subtle; here, 32 questions with warehouse-computed answers and a cost-instrumented runner will say so in about ten minutes and $10.

Recommendation

Do phase 0, then decide

I would not commit to the migration now, and I would not rule it out. The loop works, is measured at 53 of 53, and is not where the risk in this system lives. Replacing it buys maintenance you do not currently owe, and the deprecation we just tripped over is a reminder that the library’s API is itself a maintenance cost.

But phase 0 is a day and settles the two real unknowns — whether the trap prose survives custom_table_info, and whether async is workable. If both are clean, this becomes a sound call whenever engine.py next needs real work. If either is not, you have saved a week.

Reasons to move that this document cannot weigh, and that may outrank everything above: the team already knows LangChain, you want its ecosystem, or you would rather maintain configuration than a loop.
