01 · the problem

The same question, asked twice, gave two different answers

Cadence was asked why the books and the provider disagree on Harborlight for Q1 FY2024. The corpus contains the reason: a one-off catalogue licensing true-up posted to account 5000.

One run found it. The next, same model and same data, explained the variance away as structural and never surfaced the document. That is not a bug you can reproduce on demand, and not something you can demo.

Why it was hard to diagnose

Two things were being measured at once: whether the retriever can find the passage, and whether the model happened to word its search well. Each end-to-end run took ~2.5 minutes and cost real money, so the sample size was never large enough to separate them.

The two searches, side by side
Run A — found it Q1 FY2024 billing divergence Harborlight one-off catalogue licensing true-up account 5000
Run B — missed it Harborlight revenue discrepancy reconciliation internal books quarterly

Run A only knew those words because an earlier search had surfaced them. The model was, in effect, getting lucky.

02 · method

Measure retrieval on its own, and make it cheap enough to repeat

The corpus was generated with 120 facts planted at known character offsets. A hit is verified by position, not judged — so the harness can score every approach without a model in the loop, and without spending anything.

20,000documents → 119,207 chunks
98distinct questions, 197 planted spans
0.11 sto load the index, from 67 s
1.9 sto score all 98 questions
Two decisions that made the numbers trustworthy

Caching the index. Building it from the database reads 119 MB of parsed text and takes 67 seconds. Cached, it reloads in 0.11 seconds — verified to produce an identical ranking, not assumed to. That is the difference between an experiment a day and an experiment a minute, and it is why nine approaches got measured instead of two.

Unioning ground truth per question. Several questions have the same fact planted in different documents. Scoring those rows separately would count a correct retrieval of one copy as a miss on its siblings, and understate every approach equally — which looks like a fair comparison and is not.

These are not peers in the codebase, and the difference is the point

Six of the nine are Retriever implementations sharing one protocol in retrieval/retrievers.py — swap one for another and nothing else changes. The grid above makes all nine look like that.

The two that shipped are not retrievers. Ranking on the user's question is a decision in sources/corpus.py about which string to search with — no new class, no new dependency. That is why the winner cost nothing: it was never an implementation to add.

Two arms are also measured in scripts/ rather than src/. HyDE and the multi-query figures quoted here come from gen_rewrites.py and tune_retrieval.py, not the MultiQuery and QueryRewrite classes, which belong to the earlier bench_retrieval.py harness and are no longer the source of any number in this deck.

05 · dead end

Reranking and deeper pools were killed by one measurement

How deep do you have to look before the right passage appears?

0.459top 5
0.459top 50
0.469top 100
0.490top 1,000
What this rules out

A 200× deeper pool buys three points. For over half the questions the passage is not in the top thousand at all — it is absent, not ranked low. A reranker can only reorder what it is given, so no reranking budget could have recovered it. Neither could a larger TOP_K, which is free.

This is the single most valuable result in the study: it ruled out the most expensive option on the list before a cent was spent on it.

06 · dead end

Embeddings did not help, and hybrid had nothing to fuse

The question that decides hybrid retrieval is not is dense good, but is dense different. If it finds the same half that BM25 finds, combining them gains nothing.

42found by BM25 only
1found by dense only
3found by both
52found by neither
Do not generalise this

Dense retrieval failed here, for a reason specific to this corpus: 20,000 documents generated from templates share only 1,339 distinct terms, so chunks are nearly identical in meaning and embeddings have little to separate. On heterogeneous real-world prose the result would likely be very different. This is not evidence that embeddings don't work.

The one I would have shipped on reasoning alone

Query terms are matched against an index that stores stemmed words, and the matching logic reached catalogu from catalogue but never bill from billing — silently dropping the most selective term in the query. A real bug, with an obvious fix.

Fixing it properly measured worse: 0.714 → 0.694 at the ceiling, because the stems it newly reached sit in 98% of chunks. Reverted, dependency removed. Nothing but a measurement would have caught that.

08 · the winner

Search with the question the user typed

0.102→0.459

The analyst was composing its own search query, and that query was replacing the two sharpest tokens available with vaguer synonyms.

TermChunks containing itEffect
q124 of 119,207near-unique — pins the quarter
fy202440 of 119,207near-unique — pins the year
harborlight11,645useful, not decisive
202557,748matches half the corpus

Paraphrasing “Q1 FY2024” into “the first quarter” spends a 1-in-5,000 signal on a term that matches everything. The fix is to stop doing that.

Where it lives — src/cadence_backend/sources/corpus.py

No new class and no new dependency. The ranking call already existed; it was being handed the analyst's paraphrase, and now it is handed the question. Every other approach on the list would have added a module, a service or a per-query cost.

09 · recommendation

Ship the deletion. Buy nothing.

Adopt — done

Rank the corpus on the user's question. 4.5× the recall, no added latency, no added cost, one fewer moving part than the code it replaced. Verified end to end: the answer now names the account-5000 true-up that it used to find only intermittently.

Do not buy

Reranking, embedding infrastructure, hybrid indexes and per-query rewrite calls were each measured against this workload. None moved it. Together they would have added recurring cost and two new failure modes for no gain.

Invest here instead

The remaining gap is vocabulary, not ranking. Users write “our books and the provider disagree”; documents say “billing divergence”. Handing the retriever the answer's own words lifts recall to 0.714, so that is the headroom — and it is closed by changing what the documents say or by capturing better questions, not by ranking harder.

10 · limits

What this does not fix

Question styleFoundWhy
Carries an exact period label
“…for Q1 FY2024?”		 44 / 44 Two near-unique tokens pin the passage.
Conversational
“did we lose that many customers around 2025-04?”		 0 / 29 Shares no selective term with the passage, which says “cancellation spike” and “migration”.
Open, and undiagnosed

28 questions are unfindable even when handed the exact answer text as the query. Until that is understood, treat 0.714 as a soft ceiling rather than a known one.

Practical consequence: the product can make promises about questions that name a period. It cannot yet make them about loosely-worded ones.

11 · reproduce

Every figure in this deck, from three commands

# regression tests — offline, no model, no network, 1.3s
uv run pytest tests/test_retrieval_quality.py

# build the index cache once (67s), then score any approach in 1.9s
uv run python scripts/cache_index.py
uv run python scripts/tune_retrieval.py --arms bm25 --depth 1000

# end-to-end against a live backend — costs ~$0.35 and ~2 min per case
uv run python scripts/acceptance.py --dry-run

The harness lives in scripts/tune_retrieval.py; ground truth is generated by scripts/generate_corpus.py from a fixed seed, so the corpus and every number here rebuild identically.

Figures measured 27 August 2026 against 20,000 documents / 119,207 chunks / 98 planted questions. The retrieval floors are pinned in tests/test_retrieval_quality.py, so if a change moves them, the test suite says so.
