How an answer is produced

The analyst writes its own SQL and runs it. Nothing is templated, and every figure traces to a query the reader can expand.

StepWhat happens
1 · PromptTwo tools — run_sql and search_documents — plus the full schema of every registered source, including its documented traps and coverage gaps.
2 · It writes a queryThe SQL is the model’s own. It chooses the warehouse and states a purpose, which becomes the trace label.
3 · GuardMust begin SELECT or WITH; writes and USE ROLE are blocked. Defence in depth — the real boundary is a role granted SELECT and nothing else.
4 · ExecuteSupabase in a read-only transaction; Snowflake on a worker thread so one slow query cannot stall the stream. Up to 50 rows return.
5 · StreamSQL, columns and rows reach the browser immediately — before the answer exists.
6 · LoopResults re-enter the conversation and the model decides what to ask next, up to fourteen turns. Hence traces of three to fourteen steps.
7 · ComposeA separate pass shapes the answer, so composing never competes with deciding what to query.
Why this is the anti-hallucination story

Figures come from SQL that was executed, not documents that were read. That is what lets the analyst contradict a document: asked about a licensing true-up the corpus asserts, it queried the ledger, found the account was a cost line with flat postings, and rejected the claim rather than repeating it.

A tendency, not a mechanism

The cross-checks — scaling the panel against the census, counting the helpdesk two ways — are the model choosing to corroborate, encouraged by the prompt. No code enforces them. It happened wherever it was relevant, but nothing guarantees it.

Run these eight, in this order

Each was asked repeatedly against the live stack rather than once. The rate is over graded runs — runs that died on a gateway rate limit are excluded rather than scored as failures, because a spent budget is not a wrong answer.

The most important test in the set. Adding 20,000 documents gives the model far more to quote, and the risk is that it now finds something plausible-sounding and answers a question it should refuse. If this ever stops refusing, the corpus has cost us the guardrails.

03 Were Tidepool cancellations in April 2025 real churn or plan migrations? 4/4
What to watch for — expand the SQL steps
  • market_panel_sample read for the rate, rather than 281 hardcoded.
  • mv_event_monthly — the materialised view, a 287-row lookup instead of a 929k-row aggregation.
  • Sampled counts scaled to a population estimate before any comparison.

A deliberate trap. The events are a 1-in-281 panel and the aggregates are a census; comparing them unscaled understates by that factor. This is the question that shows the performance work as well as the correctness.

Before the first question

Wait for BM25 index: 119207 chunks … built in 73.9s in the backend log, roughly ninety seconds after startup. Ask before that and document search returns nothing — it degrades quietly rather than failing, which is correct behaviour but looks like the feature is missing. Confirm market_source=both on the same line: that is what puts the Supabase panel and the Snowflake ledger in reach of the same question.

How an answer is actually produced

Two mechanisms, and only one of them is retrieval. The comparison that led here — nine approaches, four ruled out — is in the separate retrieval study; this is what runs.

MechanismWhat it doesWhere
SQL, written by the analyst Produces essentially every figure. The analyst writes its own query, runs it against a read-only role, and the query and its rows appear in the trace. Supabase MARKET · Snowflake FINANCE + SUPPORT
BM25 document search Ranks 119,207 corpus chunks on the user’s question. Supporting context only — it corroborates a figure, it never produces one. Supabase corpus
The distinction that matters

Numbers come from SQL that was executed, not from documents that were read. That is why the analyst can contradict a document: asked about a “licensing true-up” the corpus asserts, it checked the ledger, found no such charge, and called the claim templated filler. A retrieval-led design would have repeated it.

What was tried and is not used

Postgres full-text search, dense embeddings, hybrid RRF fusion, cross-encoder reranking, multi-query rewriting, HyDE and query stemming were each measured and none moved this workload. The winner was a deletion — ranking on the user’s question rather than on a paraphrase the model wrote, which lifted recall@5 from 0.102 to 0.459 and is cheaper than what it replaced.

Those numbers were measured against the planted corpus, whose MARKET and SUPPORT claims are now known to be false. The relative ranking of the approaches still holds, since all were scored on identical data; the absolute figures should not be quoted as product accuracy.

Known limits — do not demo these

Both are real, both are measured, and neither is fixed by the work above.

Withdrawn — this limit was measured against fabricated ground truth

This section previously read: “conversational questions do not retrieve — 0 of 29”, presented as a hard limit of the product. It was tested and the premise did not hold.

The planted facts those 29 questions were scored against are not true. Sampled against the warehouse they describe, 0 of 8 MARKET claims and 0 of 6 SUPPORT claims are supported: the “April 2025 migration spike” sits at 6.1% annual-prior cancels against a 6.1% mean, SUPPORT.TICKET has no escalation column for an “escalation surge” to appear in, and two of those questions cite months before the ticket data begins in July 2024.

So the 0-of-29 was not a retrieval failure. Retrieving those documents would have made answers worse — the analyst would have asserted a migration that never happened. It already declines to: asked the Lumora+ question it queries prior_plan, finds 5.9% against a 5.0–7.5% baseline, and rejects the claim. It was right and the planted fact was wrong.

Resolved — both warehouses now run together

This was listed here as a hard limit: 90 of 120 planted facts depend on ledger or ticket tables that exist only on Snowflake, while the demo had to run on Postgres because that is where the corpus and the 929k events live. That framing was wrong. The two warehouses were mutually exclusive only because both SQL sources answered to the same internal id; the corpus was never tied to either.

With MARKET_SOURCE=both the analyst reaches the Supabase panel and the Snowflake ledger in one question. Verified on the flagship: it reads the ledger’s fiscal calendar, finds that Q1 FY2024 resolves to Apr–Jun 2023 before coverage begins, reconciles GL 4000 at $1,842.74m against the panel’s $1,848.28m to 0.30%, and still names the account-5000 true-up from the corpus — a sharper answer than either warehouse could give alone.

The hard ones are in there: the churn case is wrong at 4.19% if the closing base is used instead of the opening one, and the analyst returned 4.24%.

Two of those were first scored wrong — by the grader, not the app

The Snowflake run initially reported 12 of 14. Both failures were defects in the grading regexes: one could not match “$4.98bn” because b\b does not match “bn”, and the other forbade any digit near the word “tickets”, which failed an answer that correctly said “0 tickets is an absence of measurement, not an absence of contacts” and then cited the counts for months that are covered.

Re-grading the stored response text with the fixes gives 14 of 14 without re-running anything. That is the fourth grader defect in this workstream, every one failing in the same direction — scoring a correct answer wrong or a wrong one right — so the graders now carry 18 tests of their own.

Still open

28 questions are unfindable even when handed the exact answer text as the query. Until that is diagnosed, treat 0.714 as a soft ceiling rather than a known one.

Reproduce any of it

The free tiers run in seconds and need no API key.

# retrieval regression tests — offline, no model, no network
uv run pytest tests/test_retrieval_quality.py

# re-score every approach over all 98 questions
uv run python scripts/cache_index.py          # once, 67s
uv run python scripts/tune_retrieval.py --arms bm25

# end-to-end, costs ~$0.35 and ~2 min per case
uv run python scripts/acceptance.py --dry-run
uv run python scripts/acceptance.py --repeat 3

The acceptance runner classifies each run pass / fail / error and reports the rate over graded runs only. That distinction was added after it reported a case as 67% flaky when the app had answered correctly every time it was allowed to answer — the failures were a gateway rate limit, not a wrong answer.
